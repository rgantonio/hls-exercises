# Bambu RTL-only flow, tier done (BAM2 R1), 2026-11-05

The whole tier done with `bench/bambu.py`: vecadd, vecmul, vsum and dot, W in {1, 2, 4, 8, 16, 32}, sizes n64 and n512, 48 points, case `bambu` (Bambu's default setup plus `#pragma HLS unroll` on LANE), 10 ns, nangate45. Bambu builds each kernel and W once at n512 in the podman container (localhost/hls-exercises-bambu:4), without `--simulate`: 24 builds. Our SystemVerilog testbenches (tb/) then simulate each build in Questa 2022.4 on the host at n64 and n512, each with a no-stall run (cycles) and a random-stall, two-task run (pass/fail): 96 simulations. Code at c8231e0. The build tree was wiped (`rm -rf build`) before the run. Started 2026-11-04 23:52:25.

## Commands

```bash
git pull                       # main at c8231e0
rm -rf build
lmutil lmstat -a -c 1717@licserv     # msimhdlsim: 75 issued, 1 in use -> --sim-jobs 32
pixi run python bench/bambu.py run --tier done --dry-run     # 24 Bambu builds, 96 simulations
pixi run python bench/bambu.py run --tier done -j32 --sim questa --sim-jobs 32
```

Each point's Bambu command is in `rtl/done/<kernel>/bambu_w<W>/cmd.txt` (see R0, `2026-11-04_bambu_r0.md`, for the vecadd W = 8 one).

## Results

All 24 builds ok, all 96 simulations PASS, 48 of 48 points ok. All rows are portable (no vendor primitives, no SystemVerilog-only constructs). Bambu PandA 2024.10 rev c2ba6936.

**The W = 32 points pass**: all 8 (4 kernels × n64, n512), in both the no-stall and the random-stall run, on RTL freshly built at n512 and simulated in Questa. BAM1 had recorded them as failed only because of Bambu's own co-simulation (vecadd and vecmul hung, vsum and dot hit the 200M-cycle limit).

## Verilog against BAM1

For each kernel and W, `diff` of `rtl/done/<k>/bambu_opt_w<W>/<k>.v` (BAM1: built at n64, with `--simulate`) and `rtl/done/<k>/bambu_w<W>/<k>.v` (built at n512, without it), both without Bambu's two header lines. No point has any difference other than the operand order inside a SIMPLEJOIN_FU's `.ops({...})`. A second check parsed every SIMPLEJOIN_FU instance in both files: same instances, the same operand set per instance, and the rest of the file identical.

| kernel | identical | `.ops` order only |
|---|---|---|
| vecadd | W = 4, 16 | W = 1 (4 of 5 SIMPLEJOIN_FU reordered, 5 hunks), W = 2, 8, 32 (1 of 1) |
| vecmul | W = 8, 16, 32 | W = 1 (5 of 5 reordered, 6 hunks), W = 2, 4 (1 of 1) |
| vsum | all W (no SIMPLEJOIN_FU) | none |
| dot | W = 32 | W = 1, 2, 4, 8, 16 (1 of 1) |

At vecadd and vecmul W = 1 the joins combine the `done` signals of the A, B and C stream modules (`A_/B_bambu_artificial_ParmMgr_Read_axis_modgen`, `C_bambu_artificial_ParmMgr_Write_axis_modgen`). Elsewhere they join two `fu_..._P0` done signals.

The rebuilt `rtl/done/vecadd/bambu_w8/vecadd.v` differs from R0's only in the PandA header timestamp, so the same command gives the same operand order: the order changes with the command (size, `--simulate`), not from run to run.

## Questa warnings

Every one of the 96 simulations gives the same two warnings and nothing else (`Errors: 0, Warnings: 2` in all logs):

- `(vopt-2685) [TFMPC] - Too few port connections for '<instance>'. Expected 11, found 10.`
- `(vopt-2718) [TFMPC] - Missing connection for port 'out1'.`

The instance is always Bambu's write module for the output stream, whose `out1` output Bambu leaves unconnected: `C_bambu_artificial_ParmMgr_Write_axis_modgen` for vecadd and vecmul (12 builds), `out_bambu_artificial_ParmMgr_Write_axis_modgen` for vsum and dot (12 builds). At W = 1 the instance is named after the module (`C_..._48_i0`, `out_..._62_i0`); at W ≥ 2 it is a `fu_<top>_<id>` instance. No other warning appears at any point. BAM1's Verilog has the same unconnected instances (the diff above leaves them unchanged).

| kernel | W | runs with the two warnings |
|---|---|---|
| vecadd, vecmul, vsum, dot | 1, 2, 4, 8, 16, 32 | 4 of 4 (n64 and n512, stall 0 and 1) |

## Unexpected

- Two builds took about 39 s against 11 to 15 s for the rest: vecmul W = 16 and vecadd W = 32. Their FSMs are the same size as the neighbours' (8 states). I have not looked into which Bambu step took the time. It may just be contention among the 24 parallel containers.
- vecadd and vecmul at W = 1 run at 1.48 to 1.50 cycles per beat with 21 FSM states, faster per beat than at W = 2 (2.97 to 3.00, 8 states). vsum at W = 1 also has 21 states (2.50 cycles per beat). dot at W = 1 has 9 states and 3.00 cycles per beat.
- dot moves from 3 to 4 cycles per beat at W = 8, vsum at W = 16.
- Untracked `rtl/done/vecadd/opt_w8_c10/` and `rtl/done/vecmul/opt_w8_c10/` are left untouched and not committed.
